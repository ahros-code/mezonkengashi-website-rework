# MEZON KENGASHI — Islamic finance advisory, Uzbekistan

Next.js 16 App Router, Uzbek (default) + Russian.

```bash
npm install
npm run dev     # http://localhost:3000 → redirects to /uz
npm run build
npm start
```

## Routes

| Route | Contents |
|---|---|
| `/[locale]` | Home: hero, stats, services, council, process, FAQ, contact |
| `/[locale]/about` | Story, principles, timeline, numbers |
| `/[locale]/research` + `/[slug]` | Research and articles |
| `/[locale]/news` + `/[slug]` | Newsroom |
| `/[locale]/events` + `/[slug]` | Programme, upcoming and past |
| `/[locale]/faq` | Categorised questions |
| `/[locale]/talim` | Mezon Taʼlim, the education sub-brand (CPSS course, modules, instructors) |

Navigation is five items; Research, News, Events and FAQ sit under the
*Bilim markazi* dropdown. Paths are declared once in `src/lib/routes.ts`, so the
navbar, footer, sitemap and JSON-LD cannot disagree.

## Everything on the page is placeholder data

The logo, palette, typeface and contact details are the client's real ones.
Everything else is still placeholder — before launch, replace:

| What | Where |
|---|---|
| Company name, phone, email, hours (REAL values) | `src/lib/site.ts` |
| Home page copy | `src/i18n/uz.ts`, `src/i18n/ru.ts` |
| Sub-page copy (About, FAQ, listing pages) | `src/i18n/uz.pages.ts`, `src/i18n/ru.pages.ts` |
| News items | `src/content/news.ts` |
| Research and articles | `src/content/research.ts` |
| Events and training | `src/content/events.ts` |
| Client roster and certificate registry (**invented sample organisations**) | Studio → Mijozlar va sertifikatlar, or `src/content/clients.ts` |
| Council member ids + initials | `src/lib/site.ts` (`boardMembers`, `expertMembers`) |
| Council names, roles, bios, credentials | `council.members` in both dictionaries |
| Production domain | `NEXT_PUBLIC_SITE_URL` (see `.env.example`) |

`src/i18n/uz.ts` is the source of truth for the dictionary shape — `ru.ts` is typed
against it, so a missing Russian key is a build error rather than a blank spot on
the page. The same holds for `uz.pages.ts` / `ru.pages.ts`.

Content in `src/content/` keeps both locales adjacent per field
(`{ uz: "…", ru: "…" }`) rather than in parallel files, so a translation cannot be
forgotten without TypeScript noticing.

Bilim markazi content (research, news, events, FAQ) is managed in Sanity once the
CMS is configured — see [Sanity CMS](#sanity-cms). The files in `src/content/`
remain as the bundled fallback.

### Client roster and certificate registry

The home page lists every organisation the council has worked with (`Clients`),
and `/[locale]/certificates` is the public registry: search by number, name or
product, filter by status and sector, and a page per certificate at
`/[locale]/certificates/<number>` that renders the certificate as a printable
document. The home page's verify box and each roster tile link into the registry
pre-filtered (`?q=`, `?org=`).

Status is derived, not stored: a certificate is *valid* until its expiry date
(Tashkent time), then *expired*; ticking **Bekor qilingan** in the Studio makes it
*revoked* and stamps the document. The entry is never deleted, so the public record
stays honest. The pages revalidate hourly so expiries show on the day.

The organisations in `src/content/clients.ts` are **invented placeholders**. Unlike
the knowledge-centre content, an empty CMS falls back to them so the section is
never blank; the first organisation published in the Studio replaces the whole
sample set. An organisation with a logo shows it; without one it gets a monogram
in the khatam star.

### Council portraits

The council is real people, taken from mezonkengashi.uz and the client's own
reference shots. Portraits live in `public/img/council/<member id>.webp` and are
generated by `node scripts/gen-portraits.cjs` as 720px squares that fill the top of
each card. It crops each source to head and shoulders, and for the seven portraits
that arrive already cut to a circle it fills the corners by carrying each photo's own
backdrop outward from the rim. A soft edge falloff and slight desaturation are what
make ten photographers — white studio, black studio, a bookshelf, a curtain — read
as one set.

A member with no portrait sets no `photo` flag in `src/lib/site.ts` and falls back
to a procedural girih medallion with their monogram, so an incomplete roster still
looks deliberate.

### Mezon Taʼlim

`/[locale]/talim` is the education sub-brand's page. You reach it from the
featured card at the foot of the *Bilim markazi* dropdown (and the mobile menu),
the footer, and a small link in the Education tile under Services. It
deliberately does not look like the council's site. It is set at
night: dark navy grounds, the brand amber used as light, lit Registan and
Tilya-Kori photography, and pointed-arch frames. It keeps the family's colours,
Montserrat and the real Taʼlim logo (`public/brand/talim-logo.svg`, split into mark
and wordmark in `src/components/TalimMark.tsx`).

| What | Where |
|---|---|
| CPSS facts, modules, instructors, other courses, gallery slots, contacts | `src/content/talim.ts` |
| Page copy (both languages) | `talim` in `src/i18n/uz.pages.ts` / `ru.pages.ts` |
| Instructor photos (from mezon-talim.uz) | `public/img/talim/*.webp` |

**Placeholders to replace before launch:**

- The four *other programmes* are labelled samples (`sample: true`, shown with a
  *Namuna* tag). Replace them with the real courses, and delete the flag when a
  course is final.
- The gallery has five empty frames. Drop photos into `public/img/talim/` and set
  `src` (and `alt`) on each entry in `plates`.
- The standard numbers shown under each CPSS module are *examples* of real AAOIFI
  Shariʼah Standards. Have the programme director confirm which module teaches
  which standard.
- The "current cohort started 8 August" line in `talim.intake` needs updating
  each cohort.

Motion is wired once in `talim/TalimFx.tsx` through data attributes: `data-reveal`,
`data-count`, `data-words`, `data-spot`, `data-tilt`, `data-hero` and `data-sticky`.
The embers are a single canvas (`Embers.tsx`) that sleeps off screen. The module
journey (`Journey.tsx`) pins and scrolls sideways on desktop, and is a swipeable
row on phones and under reduced motion. All content is visible without JavaScript.

## Design system

Everything comes from the brandbook (`references/Mezon_Kengashi_Brandbook.pdf`):

| Token | Value | Role |
|---|---|---|
| `--kobalt` | `#003A64` | brand navy |
| `--nil` | `#00223D` | deepest navy — hero and footer ground |
| `--zar` | `#F8B700` | brand amber |
| `--paper` / `--ganch` | `#FFFFFF` / `#EEF1F5` | light grounds |

Every other token is a tint or shade of those three — there is no fourth hue.

Type is **Montserrat**, the brandbook face, in 400–800. Its `latin` subset covers
`U+02BB–02BC`, so Uzbek `oʻ` / `gʻ` render correctly. **Prata** survives in exactly
one place — the pull-quote inside articles (`--font-accent`) — as the small amount
of secondary type the client allowed. If you drop that usage, remove the font from
`src/app/[locale]/layout.tsx` too rather than shipping an unused download.

### Logo

`scripts/build-brand-assets.js` regenerates `public/brand/` from the
supplied `references/logo horizontal svg.svg`: it splits the mark from the wordmark
and emits the horizontal lockup, an all-white monochrome lockup for dark grounds,
the mark alone, the stacked (primary) lockup rebuilt as vector, and the favicon.

The navbar and footer use `mezon-logo-dark.svg`: the navy parts go white so they
read on the navy ground, while the amber stays amber, so both brand colours are
present. The strict brandbook dark-ground variant is all-amber (`RANG VA MONOXROM`)
— swap the src to `mezon-logo-mono.svg` or regenerate an amber lockup if the client
prefers that. The *CHEKLOVLAR* page rules out gradients, re-ordering and off-palette
tints in any case.

The favicon (`src/app/icon.svg`) is the mark on a transparent ground, with a
`prefers-color-scheme` rule that flips the navy strokes to white in a dark tab strip.

The geometric spine is a khatam (8-point star) tessellation computed in
`src/components/Girih.tsx` — the same construction generates the page background
lattice, the service icons, the process nodes, the FAQ markers, the news and event
date plates, and the council medallions. Tokens and shared materials (`.glass`,
`.grain`, `.rule`, `.btn`) live in `src/app/globals.css`; everything else is a CSS
Module.

Sub-pages share `PageHero` (the lapis band), `Prose` (article body blocks) and
`ArticleView` (the reading layout) so they read as one site, then differentiate
below the fold: research is editorial, news is a dated broadsheet, events are
lapis cards with a date plate, FAQ is a sticky index over stacked accordions.

**Four gotchas, all load-bearing:**

1. Turbopack's CSS Modules rewrite `animation-name` even for keyframes declared in
   `globals.css`, so a module referencing `rise` gets a hashed name that resolves
   to nothing. Any keyframe a module uses is declared in that module. Don't "clean
   up" the duplication.
2. `.glass` is written as `:where(.glass)` so component modules can override
   position, radius or overflow without a specificity fight — bundle order between
   globals and modules is not stable. Because `:where()` is zero-specificity, the
   `button` reset is wrapped in `:where()` too, or it would strip the glass off the
   burger. `.btn` deliberately stays a normal class: `body { color }` is an element
   selector and would otherwise beat it.
3. The navbar contracts on scroll using `transform` on the row, not `padding` on
   the header, so scrolling never forces layout on a fixed element.
4. Anywhere a module class must beat a global one (`.cta` vs `.btn`, `.pill` vs
   `.glass`), the module rule is scoped to a parent so it wins on specificity
   rather than on bundle order, which is not stable between builds.

Motion: one orchestrated hero load sequence, slow ambient drift on the lattice,
and everything else driven by pointer, scroll position or form state. All of it
collapses under `prefers-reduced-motion`.

## SEO

- `/uz` and `/ru` are statically generated; `/` negotiates from `Accept-Language`
  via `src/proxy.ts`.
- Per-page, per-locale title, description, canonical and `hreflang` alternates
  including `x-default`.
- Titles use a short `%s | MEZON` template; pages whose own title already names the
  brand pass `titleAbsolute` to skip it and stay inside ~60 characters.
- `src/lib/jsonld.ts` builds every graph from the same content the page renders,
  so structured data cannot drift from visible copy:
  - home — Organization + ProfessionalService + LocalBusiness (address, geo,
    opening hours, the seated council as employees, 6-service offer catalog), WebSite, WebPage,
    FAQPage, HowTo
  - about — AboutPage; faq — FAQPage
  - index pages — CollectionPage with an ItemList of their entries
  - research — ScholarlyArticle; news — NewsArticle (author, dates, word count)
  - events — EducationEvent with attendance mode, location and a UZS offer
  - every sub-page also emits a BreadcrumbList
- `sitemap.xml` covers all 22 paths across both locales with per-URL language
  alternates; plus `robots.txt`, a generated `opengraph-image` per locale, and an
  SVG favicon.
- Both council tab panels render into the HTML (the inactive one is `hidden`), so
  all eight names are crawlable without executing JS. The same applies to the FAQ
  page: every category and answer ships in the markup.

## Section backdrops

`SectionBackdrop` gives otherwise plain sections something to sit on: a faint
khatam lattice, a soft wash in the brand colours, a hairline arc echoing the
logo, and optionally a photograph pushed almost all the way back. `placement`
(`right` / `left` / `band`) moves where the weight falls so no two sections look
alike, and `id` must be unique per page because it names the SVG pattern.

Host sections need `position: relative; isolation: isolate; overflow: clip` — the
backdrop sits at `z-index: -1` so static content stays above it without every
container having to be positioned.

## Sanity CMS

Bilim markazi — tadqiqotlar, yangiliklar, tadbirlar and savol-javob — is edited in
[Sanity](https://www.sanity.io). The Studio is embedded in this app at **`/studio`**,
so editors work on the site's own domain and there is no second deployment to keep
in step with the schema.

### The site runs without it

With `NEXT_PUBLIC_SANITY_PROJECT_ID` unset, every content getter in
`src/content/source.ts` returns the files in `src/content/` and the dictionaries in
`src/i18n/`. Local work and CI need no credentials, and a CMS outage degrades the
live site to its last bundled copy rather than to a 500.

### Setting it up

1. Create a project at [sanity.io/manage](https://www.sanity.io/manage). Note the
   **project id** and keep the default `production` dataset.
2. Copy the values into `.env.local` (see `.env.example`):

   ```
   NEXT_PUBLIC_SANITY_PROJECT_ID=abc12345
   NEXT_PUBLIC_SANITY_DATASET=production
   ```

3. Add `http://localhost:3000` and the production origin under **API → CORS origins**,
   both with credentials allowed. Without this the Studio cannot log in.
4. Seed the dataset with the content already on the site:

   ```
   SANITY_WRITE_TOKEN=... npm run sanity:seed
   ```

   Ids derive from slugs, so re-running is idempotent. `-- --force` overwrites
   documents that already exist.
5. Open `/studio`, sign in, and check the content came across.

### Roles

Sanity's built-in project roles cover what this site needs — custom roles are an
Enterprise feature and are not required.

| Person | Role | Can |
|---|---|---|
| Owner | **Administrator** | Everything, including inviting people, tokens, datasets and billing |
| Content team | **Editor** | Create, edit, publish and delete content; cannot manage members, tokens or datasets |

Invite at **sanity.io/manage → your project → Members → Invite**, choosing *Editor*
for everyone who is not the owner. Roles are enforced by Sanity's API, not by this
codebase, so an Editor cannot get administrator access through the Studio UI.

If you later want someone who may draft but never publish, Sanity's **Contributor**
role does exactly that.

### What the CMS owns

| Studio section | Document type | Renders on |
|---|---|---|
| Tadqiqotlar va maqolalar | `researchArticle` | `/[locale]/research` |
| Yangiliklar | `newsArticle` | `/[locale]/news` |
| Tadbirlar | `event` | `/[locale]/events` |
| Savol-javob boʻlimlari | `faqCategory` | `/[locale]/faq` |
| Sahifa matnlari | `researchPage`, `newsPage`, `eventsPage`, `faqPage` | the four listing pages |

Page-copy documents are singletons: one fixed document id each, not creatable from
the "new document" button and not deletable, because a second one would be invisible
to the site while looking perfectly valid in the Studio.

Only **editorial copy** lives in the CMS — headings, ledes, meta title and
description, section labels, the FAQ closing block. Interface chrome that repeats
across the site (button words, "N daqiqalik oʻqish", the event format names) stays
in `src/i18n/`: it is part of the design, it changes when the design changes, and
putting it in front of an editor invites a half-translated interface.

Page copy is *overlaid* on the dictionary — an empty field in Sanity falls back to
the shipped copy, so a page can move into the CMS one field at a time.

### Bilingual content

Every translatable value is one object with a `uz` and a `ru` field, mirroring the
`L` type the site already uses. Editors see both languages side by side in the same
form, and validation refuses to publish with either half empty — a half-translated
page is worse than an untranslated one, because the reader only finds the gap after
clicking through.

### Article bodies

Article bodies are a typed array of four blocks — paragraph, heading, list, quote —
not Portable Text. That is deliberate: rich text would let an editor paste headings
six levels deep, tables and images that `ArticleView` would silently drop. The four
blocks are exactly what the design can render.

### Publishing and cache

Queries are tagged and revalidate every 60 seconds (`REVALIDATE_SECONDS` in
`src/sanity/client.ts`), so a publish reaches the site within a minute with no
redeploy. For instant publishing, point a Sanity webhook at `/api/revalidate`:

- **URL** `https://<site>/api/revalidate`
- **Trigger** Create, Update, Delete
- **Secret** the same value as `SANITY_REVALIDATE_SECRET`

The route verifies the signature, so the endpoint is safe to expose.

### Layout of the integration

| File | Purpose |
|---|---|
| `sanity.config.ts` | Studio config: schema, structure, singleton guards |
| `src/sanity/env.ts` | Connection details and `isSanityConfigured` |
| `src/sanity/schema/` | Document and object types |
| `src/sanity/structure.ts` | Studio sidebar, mirroring the site's own navigation |
| `src/sanity/queries.ts` | GROQ, projecting Sanity's shapes onto the site's types |
| `src/sanity/client.ts` | Fetch with revalidation and fallback-on-error |
| `src/content/source.ts` | The one door between pages and content |
| `src/app/studio/[[...tool]]/` | The embedded Studio route (client-only) |
| `scripts/seed-sanity.ts` | One-off migration of the bundled content |

Two build notes worth keeping: `sanity` is listed in `serverExternalPackages`
because bundling it into the RSC graph makes Turbopack resolve `swr` under the
`react-server` condition, where the default export Sanity imports does not exist;
and the Studio is loaded with `ssr: false` because server-rendering it leaves React
without an active dispatcher.
